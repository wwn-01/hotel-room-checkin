## 一、测试工具介绍

1. **pytest**：Python 测试框架，用于组织并执行单元与接口测试用例，通过断言判断实际结果是否符合预期，便于反复回归验证。
2. **Apifox**：API 调试与接口管理工具，用于手工构造 HTTP 请求、查看状态码与响应字段，验证接口契约、参数校验与权限控制。
3. **flake8**：Python 静态代码检查工具，用于检查代码规范（PEP 8）、未使用导入和潜在语法问题，保证测试脚本与源码的可读性。

## 二、测试内容

### 1. 房态查询

- 接口：`GET /rooms`、`GET /room/{room_id}`。
- 测试点：登录后可获取房间列表与指定房间详情；返回字段包含房号、状态等；未登录或普通用户访问受限接口时返回相应拒绝状态码。

> 【截图：房态查询接口请求与响应】

### 2. 房间锁定

- 说明：当前 MVP 未提供独立的“锁定房间”接口，房间状态由管理员通过 `PUT /room/{room_id}/status` 更新（如“维修中”“清扫中”）。
- 测试点：管理员更新房间状态返回成功；普通用户调用该接口被拒绝（403）；状态变更写入审计日志，可通过 `GET /logs` 查看。

> 【截图：房间状态更新与权限校验结果】

### 3. 入住冲突（一房多住校验）

- 说明：当前系统按课程要求只输出入住建议，不执行真实占房与开锁，因此未实现“一房多住”的强拦截。
- 测试点：对同一房间重复调用 `POST /room/{room_id}/checkin`，校验返回结果一致；不符合入住条件时自动生成质检复查工单，并记录审计日志。真实并发占房冲突校验待后续版本补充。

> 【截图：重复入住校验与工单生成结果】

### 4. 办理入住接口

- 接口：`POST /room/{room_id}/checkin`。
- 测试点：可入住房间（清扫完成且质检通过）返回 `can_checkin=true`；未质检房间返回 `can_checkin=false` 且生成 `auto_workorder_id`；不存在的房间返回 404；响应中 `action` 字段明确“仅提供建议，实际入住/开锁须人工确认”。

> 【截图：办理入住接口成功与失败用例】

## 三、测试结果描述

- **pytest**：`tests/` 目录下的用例覆盖登录鉴权、角色权限、知识库问答等模块；执行后断言结果符合用例预期，无失败用例。
- **Apifox**：按上述接口逐项调试，状态码与响应字段符合设计；普通用户访问管理员接口返回 403，输入为空或参数超限时返回 422，权限与参数校验生效。
- **flake8**：对 `src/` 与 `tests/` 下的 Python 文件进行规范检查，未发现语法错误；按提示调整了个别格式问题。
- **业务链路**：房态校验闭环通过——可入住房间校验通过，未质检房间校验不通过并自动生成工单，符合“智能体只给建议、异常转人工”的设计约束。

> 【截图：pytest / flake8 运行输出】

## 四、测试小结

本次使用 pytest、Apifox 和 flake8 三种工具，从代码规范、接口功能和业务规则三个层面对系统进行了验证。测试结果表明，房态查询、状态更新、入住校验及权限控制均能按预期工作，知识库问答与工单联动逻辑符合课程要求。

同时也要看到，当前版本属于 MVP：房间锁定、真实办理入住和“一房多住”强冲突拦截尚未实现，系统只提供建议、不执行开锁，相关测试以接口契约和重复校验方式覆盖。后续若继续开发，应补充真实入住状态机与并发冲突校验，并增加自动化回归用例。
