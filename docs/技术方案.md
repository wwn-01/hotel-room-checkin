# 山海旅居 · 房态与入住协同智能体系统 技术方案
## 1 项目背景
来源于业务访谈报告，酒店现存核心问题：原有 PMS 系统仅单一房态字段，无法区分【已清扫】【已查房】【可售】。客房清扫上报就标记房间可入住，但质检查房未完成，造成前台误判，客人到店无法入住，产生等待、换房客诉。

业务目标：
- 高峰入住等待时间：38 min → 15 min
- 每周房态错误次数：24 次 → 5 次
- 试点验收：周末连续 4 周，房态误判为 0；异常场景完整留痕；异常强制转人工。

参与角色：顾明岚（运营经理）、林亦舟（前台）、唐映秋（客房调度）、秦芮（PMS 工程师）、傅景（服务质量专员）、叶书（客人体验主管）

业务硬约束：AI 智能体**仅提供解释、提醒**，不自动分房、不开门锁，不处理客人身份认证。

## 2 系统总体定位
基于 Python 3.11 + FastAPI 实现后端接口服务。
1. 管理房间多状态：已清扫 / 已查房 / 可售 / 维修中
2. 管理查房待办任务，待办必须确认接手人才算完成，仅发送消息不算完成。
3. 智能体输出房态解释、风险提醒，不执行业务变更。
4. 全部操作写入审计日志，支持事后审计回溯。
5. 异常场景（维修房解封、版本冲突、资料缺失）强制流转人工处理。

## 3 权限设计
|角色|可读权限|可写权限|
| ---- | ---- | ---- |
|前台接待员|查询房态、查看提醒|无写权限|
|客房调度员|房态、待办列表|上报清扫、分配查房待办、确认接手人|
|服务质量专员|全部日志、全部房态|暂停试点、审核异常工单|
|PMS 工程师|配置信息|修改系统配置，不可修改业务|
|运营经理 / 客诉主管|指标统计、审计日志|无业务写权限|

> 约束：所有写操作必须校验登录角色；不可逆业务操作，必须人工确认。

## 4 数据库设计（SQLite）
### 4.1 room 房间表
- room_id：房间编号，主键
- room_status_clean：bool，是否清扫完成
- room_status_check：bool，是否质检查房通过
- room_status_sell：bool，是否可售
- room_maintain：bool，是否维修封锁

### 4.2 task 待办任务表
- task_id：主键
- room_id：关联房间
- task_type：清扫 / 查房 / 异常复核
- assignee：接手人账号
- is_confirm：bool，是否确认接手
- create_time：创建时间
- finish_time：完成时间
- remark：备注，退回时填写退回原因

### 4.3 audit_log 审计日志表
- log_id：主键
- biz_no：业务编号
- biz_version：资料版本号
- operator：操作人账号
- operate_content：操作内容
- change_before：变更前数据
- change_after：变更后数据
- create_time：时间戳

## 5 核心接口清单
> 全部接口统一返回格式：`{"ok":bool,"data":...,"error":{"code":"","msg":""}}`

1. GET `/api/room/{room_id}` 查询房间房态信息
2. POST `/api/task/clean_report` 客房清扫上报
3. POST `/api/task/check_report` 质检查房结果上报
4. POST `/api/task/assign` 分配待办任务
5. POST `/api/task/confirm` 待办任务接手确认
6. GET `/api/audit/log` 获取审计日志（仅授权岗位）
7. GET `/api/agent/remind` 获取智能体房态提醒（AI 只输出文字提醒，不修改数据）

## 6 关键业务规则
1. 房间可售（room_status_sell=True）的前置条件：清扫完成 AND 查房通过，缺一不可。
2. 查房待办，必须 assignee 确认接手 `is_confirm=True`，任务才算正式分配完成，仅创建消息不算。
3. 维修房解除封锁，自动生成异味复查待办，未复查完成，房间不可售。
4. 发生：维修解封漏复查、数据版本冲突、资料缺失 → 生成人工异常工单，智能体禁止给出自动处理建议。
5. agent 智能体接口，只返回文本提醒，不会调用任何修改数据库接口。

## 7 试点验收标准
1. 业务指标：周末连续 4 周试点，房态误判为零。
2. 技术指标：每一次业务变更完整写入 audit_log，可以完整回放预订‑清扫‑查房‑入住‑回访全链路。
3. 停止条件：出现严重质量事故，服务质量专员可以触发暂停试点。

## 8 部署运行约束
1. Python 版本固定 3.11；
2. 配置存 `config.yaml`，禁止硬编码密钥；
3. 不引入 Redis、MySQL 等额外中间件，使用内置 SQLite；
4. 所有函数必须带中文 docstring；权限、人工确认关键位置增加行内注释。
